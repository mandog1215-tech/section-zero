The Engine Laboratory

What each game's engine actually is — from the studio Engine Registry, the authoritative record.

Two of the studio's games carry the name Halcyon on their engine layer. This page exists so that name is never allowed to imply more than the evidence supports. The registry's standing finding, in full:

The three games' rendering/engine layers are maintained as independent implementations.

Verified: a comparison of every source file across the three projects (MD5, whole files) found no byte-identical source files in any pairing.

Not established: whether fragment-level reuse, adapted code, or common code ancestry exists between the projects. The comparison compared whole files byte-for-byte; it cannot rule out copied or adapted fragments, and no fragment-level investigation has been performed.

Conclusion: a cross-project audit (2026-11-01) found no evidence establishing a shared engine codebase or a common code lineage. That is the accurate claim — it is not a proof that no code was ever copied or adapted.

Sharing the Halcyon name does not establish shared code, shared ancestry of code, portability of fixes, or comparability of version numbers: a version number in one game implies nothing about any other game. What the games genuinely share is conventions — C11 throughout (SDL2 in these three; the newest game, LONGSHOT, builds on SDL3), procedural assets only, and the Section Zero boot card — each implemented independently, three times.

Per-engine records

Lineage — documented

Blacksite — Halcyon Engine 3.0

Grok Bot's engine for Blacksite, with a recorded lineage in the game's changelog: Claudio Engine 1.0 → Claudio Engine 2.0 → Halcyon Engine 3.0 (renamed at game 1.5.0, commit 8836b9a). Limit, stated in the registry: this repository's history begins at the 1.3.0 transfer snapshot, so the 1.0/2.0 era is attested by the changelog rather than by commits in the repo — partially verified. One recorded wart: a comment in the engine header calls the predecessor "Halcyon Engine 2.0" where the changelog and rename commit say Claudio 2.0. It is recorded here, not polished away. Detail: Blacksite — game & engine.

Lineage — none recorded

AirportSim — Halcyon 2.5D, version 2.5.0

The name arrived as a boot/branding module (src/engine/ = halcyon.h + boot.c: studio card, dev overlay, credits) added to an already-working renderer, in commit 626ec77 (2026-10-29). The version constant has exactly one commit in its history: it was "2.5.0" from its first commit and has never changed. No 1.0 or 2.0 exists anywhere in that project's history or changelog — the number has no recorded lineage, and why it was chosen is not recorded. It is not a point on Blacksite's scale.

Shelved project — inspected, not developed

WorldForge — no engine name

The word "Halcyon" appears nowhere in WorldForge's code or records. Its rendering layer is its own, written for that game from its founding commit. The registry deliberately assigns it no name: naming a shelved, frozen codebase from outside would invent history. If development ever resumes, naming its layer is a decision for that time.

The engine verdict — AirportSim, 2026-11-01

Alongside the registry, the studio ran a full engine assessment and mathematics audit of AirportSim on 2026-11-01 — the engine's structure, the simulation's mathematics, and the evidence beneath both examined end to end. The verdict was RETAIN the engine: keep the existing engine and simulation architecture, and build on it. That verdict stands behind everything the current programme has done since — Development Mode was grown onto the retained engine, not written around a replacement.

Evidence classes — a native-Windows product, developed on Linux

The studio's games are native Windows products developed on Linux, so engine and game claims are graded by the evidence class that supports them. Four classes, in ascending order of weight:

Evidence classWhat it establishes
Linux testsThe code's behaviour under the full test suites on the development platform — the everyday gate every change passes.
MinGW cross-compileProducibility only: the Windows binary can be built from the source. It says nothing about how the game runs.
WinePreliminary runtime evidence under a compatibility layer. It is never called Windows verification, on this site or anywhere else.
Native Windows runtimeThe product running on its actual platform. This is a release gate — for AirportSim it was exercised by the native Windows battery on the owner's test rig, on every merge, until 2026-11-10, when the owner made the game Linux-only and retired the gate; its checks now run on GitHub-hosted Linux machines. (LONGSHOT is a Linux product from its first day, so for it the native-runtime class is Linux itself.)

The grading discipline is the point: a claim is only ever stated at the class its evidence earned. The studio's five engineering principles — simulation-first engineering, evidence over appearances, causality over superficial functionality, autonomous execution with explicit authority, and one methodology with game-specific engineering — are recorded on the studio page.

How the registry is kept

  • Constants are authoritative; the registry mirrors. Each game's in-code version constant is the source of truth; the registry is updated at milestone closeouts — never the reverse.
  • No propagation. Because no shared engine codebase is established and the implementations are maintained independently, an engine change in one game neither needs nor gets porting. A defect pattern genuinely appearing in two games is handled as a studio advisory, fixed per game under that game's own gate.
  • No synchronized versions, no engine codenames, no backfilled history — each solves a problem the evidence does not show.
  • The unification tripwire. If future work ever proposes sharing an actual code component between games, that proposal must supply its own engine-level tests, version pinning, per-game integration evidence, and a priced cost analysis. Until then, there is nothing to safeguard, and nothing is built for it.

Source of truth: the studio Engine Registry (established 2026-11-01), itself grounded in the cross-project Halcyon audit and its review of the same date.
