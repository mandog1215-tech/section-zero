In design — commissioned 2026-11-07

The new save system

The current save format is one raw memory dump: it has no field encoding, so almost every major update has broken it, and one old version's file can crash the game from the load screen itself. The replacement is a clean-sheet design, not another patch: a file of named, individually versioned sections, each written field by field; a loader that cannot crash — a damaged section resets with a warning and the rest of the save loads; and exactly one one-way importer that converts old saves (versions 4–13) a single time, after which the old format is retired. It is in design now; the build follows the in-game frame. After it: real airport layouts, then collision physics.

Completed 2026-11-02 — FND-002 solved (PR #24; issue #15 closed)

The save/reload continuation investigation (issue #15)

A reloaded game continued slightly differently from one that was never interrupted. The divergence was measured, not anecdotal: it began at the first step after reload, and the first differing byte sat in the economy's double-precision region. One suspect — a private random stream — was eliminated experimentally as the sole cause; the cause was then attributed: a minute's weather was being computed from the fractional clock, so the moment of a reload shifted the weather the game continued under. The fix evaluates each minute's weather at the minute's start, and a reloaded game now continues byte-identically to one that never stopped. The owner unparked this investigation on 2026-11-02, rated it a crucial fix, and placed it first after the integration — which completed the same day. After it came the Windows verification work (stage below) and then WP-09 (see the WP-09 stage above).

Phase 0 · Route decided 2026-11-02

M2 — Windows verification path

The route is decided: (a) — the GitHub-hosted Windows runners already used by CI — extended into a scripted native test harness: build, launch, scripted scenarios, a save/load round-trip in the real save location, and automated frame capture with blank/size checks. The owner's own PC stays out until release. Cross-compilation alone will never be called verification.

Interim evidence (2026-11-02): the owner played a pre-adoption Windows build (0.5.4, built by the original author) for about an hour at Detroit — it launched and played correctly; its graphics looked somewhat low-resolution (presentation only). A first comparison since (2026-11-03) checked the current build's captured frames pixel-by-pixel across platforms: static screens are byte-identical on Windows and Linux, and all other differences sit inside live content — so the renderer is exonerated. A follow-up code check (2026-11-03) then closed the display-scaling half of the question: the current build already carries the full high-DPI setup (per-monitor DPI awareness, the SDL hint, and the high-DPI window flag), so Windows display scaling is exonerated too. What remains open is the game's own presentation — at interface scales above 100% the world view is drawn on a logical canvas and stretched, while the interface stays crisp — to be judged at the owner's hands-on with the private test build. Saves were not tested, and the current code's Windows build has never run natively — so this is provisional demonstration for an older build, not verification of the current one.

Update (2026-11-02/03): the harness was built, merged (PR #25), and demonstrated — the current code runs natively on Windows under the scripted battery, save/load round-trip included. The route then changed on the owner's instruction: all checks moved to a self-hosted rig on the owner's PC (PR #29) and the GitHub-hosted runners were removed; the native battery's home is now that rig, where the full six-job battery — the native session included — runs for every pull request.

Gate: a recorded Windows session of the current code — launch, data and layouts found, gameplay, save/load — at a real airport layout.

Rules this map follows

  • Every milestone gets its own acceptance criteria before work starts; a milestone is complete only when its criteria pass with evidence.
  • Criteria are never weakened to obtain a pass; a blocked gate is documented, not walked around.
  • Nothing that already works gets rebuilt; nothing new is stacked on a known weak point until the weak point is fixed.
  • No delivery dates are invented; the milestone order is not silently changed.
  • Statuses update at milestone closeouts, from the development record.
